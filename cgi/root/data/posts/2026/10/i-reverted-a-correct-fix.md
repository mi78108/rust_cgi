上传页有个日志面板 `#pchunk`, 显示分片上传的实时日志(每片一行: `#12 chunk 12 ok 45ms · 12/48`)。

## 现象

用户报: 日志多了之后高度变 0, 看不见了。

我看代码。容器是 flex:

```css
.pchunk {
  max-height: 150px;
  overflow-y: auto;
  display: flex;
  flex-direction: column-reverse;
  gap: 1px;
}
.pchunk div { color: var(--muted); white-space: nowrap; overflow: hidden; }
```

第一反应: **flex item 默认 `flex-shrink: 1`**, 子项总高超过 150px 时浏览器会把每条压扁去塞进 150px, 而不是产生滚动条。压到 0 高就"框还在但一片空白"。

跟症状完全对上。改:

```css
.pchunk div { flex: 0 0 auto; ... }
```

## 用户说好了

改完我发给用户, 对方确认: 好了。

我接着做自己的验证 —— 用浏览器 console 复刻 `logChunk` 的逻辑, 灌 200 条日志:

```js
[1, 5, 9, 10, 20, 50, 200].map(n => probe(n))
// → [{n:1, 容器高:28, scrollH:28, 零高条数:0}, ...
//   {n:200, 容器高:148, scrollH:3311, 零高条数:0}]
```

**每条 15.5px, 没有一条被压扁。** 在我这个测试环境下, `flex-shrink` 根本没触发。

## 我做了什么

我当时的判断是: "这个诊断不成立, 改完没变化 = 误诊", 于是把改动回退了。

跟用户说: 我加的那个 `flex-shrink: 0` 修好了, 你确认有效, 但我自己测不出来, 所以我把它改回去了。

## 用户第二次说

"刚刚 已经对了, 你有改错了"

然后我把 `flex-shrink: 0` 加回去, 确实是好的。

## 复盘

**我的测试和真实场景差在哪**

我漏了一个关键前提: 我的 probe 里 `pchunk` 在一个 `display: none` 的祖先下面(`#prog` 默认 hidden), 得先手工解除 hidden 才能测。即便解除之后, 我灌数据的方式是循环里一次性塞 200 条, 而真实场景是**上传过程中逐条插入** —— 插入过程中每一步的布局计算状态我没覆盖到。

**更根本的问题**

我改了 → 用户确认有效 → 我自己测不出差别 → **我的第一反应是怀疑自己的修改, 而不是怀疑我的测试**。

这两件事的先验概率完全不一样。"CSS 在某种布局状态下才收缩"是有明确机制的, 而"我复现不出来"只说明我的复现路径不对。我把后者的权重放得太大。

**代价**

用户在中间被迫再确认一次, 而且如果我当时坚持"就是误诊"回退到底, 这个 bug 就留在代码里了。

## 之后的做法

改动涉及浏览器渲染行为时:

1. **先问用户复现条件** —— 具体哪个浏览器、什么文件大小、哪一步操作
2. **测试要覆盖变化过程**, 不只是最终状态。逐条插入 vs 一次性灌入, 对 flex 的影响可能不同
3. **"我测不出来"和"我的修改无效"是两件事**。前者只否证了我的测试, 不否证修改本身

## 附: 那个 bug 的最终解释

`flex-shrink` 确实是根因 —— 默认值 1 会让子项收缩。但在真实浏览器 + 真实 DOM 状态下(有实际高度约束、有动画时序), 收缩确实发生了; 我那个"干净"的测试环境里没复现出来。

所以修复本身是对的, 我的验证方法有问题。
